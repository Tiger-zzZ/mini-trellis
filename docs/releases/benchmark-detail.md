# mini-trellis 与 Trellis 对比评测详细记录（Claude Code）

这次评测的目标很直接：在**同一套项目代码、同一份 `.trellis` 业务知识库、同一个 Claude Code、同一个模型与思考程度**下，实测把项目接入从 `Trellis` 换成 `mini-trellis` 后，完成同样的开发任务能不能更快、更省 Token。

测试涵盖空载启动、日常写代码、查项目规范、按规范写实现，以及跨会话记规则与迭代修改，共 6 组任务，每组独立跑 3 次。结果显示：在两边自动检查全部通过的前提下，**`mini-trellis` 在每一组任务上都比 `Trellis` 更快、处理 Token 更低；全部任务累计耗时减少 38.4%（提速 1.62×），累计处理 Token 减少 40.1%（少用 162.7 万 Token）。**

---

## 一、评测前提与环境配置

为了保证对比公平，除了安装的工具本身不同之外，其余所有条件完全一致，每次测试都在全新初始化的独立项目目录与独立宿主历史目录中运行：

| 评测维度 | 固定配置 / 对比项 | 具体说明 |
| --- | --- | --- |
| **评测目的** | `mini-trellis` vs `Trellis` 端到端效率对比 | 检验去掉重型阶段工作流、改为轻量记忆层后，实际完成任务的耗时、轮次与 Token 开销差异 |
| **对比对象** | `mini-trellis v0.3.1` vs `Trellis v0.7.0-beta.4` | 均在空白 Git 仓库中执行标准初始化（`init --claude --yes`），各自加载默认 Hook、脚本与指令模板 |
| **宿主与模型** | Claude Code `v2.1.306` + `deepseek-v4-flash` | 统一开启最高思考程度（`--effort max`），使用相同的无头调用参数，单任务超时与环境完全一致 |
| **项目代码与知识库** | 同一套 Python 业务代码 + 同一份 `.trellis/` 资料 | 包含 3 个待实现/修改的 Python 模块（`label_utils.py`、`pipeline_impact.py`、`retry_policy.py`）、4 份后端规范（`.trellis/spec/backend/`）与 1 篇背景研究笔记（`.trellis/research/`），两边业务文件字节完全一致 |
| **二者的核心差异** | 启动注入体积与查找方式不同 | `mini-trellis` 会话启动仅注入约 **1,173 字符**（目录说明 + `mem recall` 按需检索入口）；`Trellis` 会话启动注入约 **8,674 字符**（包含完整工作流手册与状态说明），并在项目下生成默认引导任务目录 |

> **统计口径说明**：耗时为命令启动到退出的实际墙上时间（秒）；轮次为 Claude Code 统计的交互轮数（`num_turns`）；处理 Token 为单次任务处理总量（`未缓存输入 + 输出 + 缓存命中读取`，其中输入与缓存互斥，不重复计算；处理 Token 衡量上下文处理总量，不等同于 API 账单费用）。

## 二、整体评测结果与图表对比

![mini-trellis 与 Trellis 在 Claude Code 上的实测耗时与 Token 消耗对比](../assets/v0.3.1-benchmark-zh.svg)

全部 6 组任务（每组 3 次，含 15 次单会话任务与 3 条四阶段跨会话长链，每侧各 27 个独立会话）整体表现如下：

- **总耗时减少 38.4%（快 1.62 倍）**：完成全部评测任务，`mini-trellis` 总计用时 **472.2 秒**，`Trellis` 总计用时 **766.5 秒**，累计节省 294.3 秒。
- **总处理 Token 减少 40.1%（少用 162.7 万）**：`mini-trellis` 累计处理 **2,426,377** Token，`Trellis` 累计处理 **4,052,930** Token。无论是未缓存的新鲜输入、模型输出还是多轮累积的缓存读取，`mini-trellis` 在每一项任务上都低于 `Trellis`。
- **总交互轮次减少 27.8%**：`mini-trellis` 累计 **273 轮**，`Trellis` 累计 **378 轮**，少走了 105 轮探索和读写。

**为什么 `mini-trellis` 更快、更省？**
1. **启动底噪更小，每一轮背负的上下文更轻**：从 `O00` 可以直接看到，哪怕什么文件都不读，`Trellis` 首轮注入的 8,674 字符也会让初始输入多出近 2,000 Token；一旦进入多轮工具调用（如 `I01`、`M01` 动辄 15～20 轮），首轮多出来的数千 Token 会在后续每一轮缓存读取中被反复累加。
2. **定位直接，少了无关目录排查**：提示词里不直接告诉模型文件名时，`mini-trellis` 通过 `mem recall` 或精简入口直接定位 `.trellis/spec/` 下的目标规范；而 `Trellis` 经常顺着启动说明去翻找 `.trellis/tasks/00-bootstrap-guidelines/prd.md` 等任务引导目录，多花了好几轮 `grep`/`Read` 和模型输出。

## 四、跨会话记规则与迭代汇总（`M01` 四阶段长链）

### 题目设计
`M01` 模拟真实开发中最常见的“多会话知识沉淀与变更”闭环。在同一项目内连续开启 **4 个全新的独立会话**（后一个会话没有前一个会话的聊天上下文，只能靠项目里沉淀的文档、日志或记忆检索获取信息）：
1. **阶段 1（记下初始规则）**：告知模型回调重试规则改为“transient 失败最多尝试 2 次，permanent 尝试 1 次”，要求更新项目知识并留一条开发日志（journal）。
2. **阶段 2（新会话按规则实现）**：开启新会话，不提示次数，只让模型“按项目当前确认的规则实现 `retry_policy.py` 的 `max_attempts` 并写测试”（验收要求 `transient -> 2`）。
3. **阶段 3（新会话变更规则）**：开启新会话，告知因“上游已经确认幂等保障”，`transient` 总尝试次数改为 4 次，要求更新原主题知识并留开发日志说明变更原因。
4. **阶段 4（新会话按新规则更新实现）**：再次开启新会话，让模型按最新确认的规则更新 `retry_policy.py` 与测试（验收要求 `transient -> 4`）。

### 整链与四阶段对比汇总

3 条完整四阶段长链跑下来，两边在阶段 2（2 次）和阶段 4（4 次）的代码验收全部通过，但在**维护项目知识与跨会话复用的成本**上拉开了明显差距：

### 3 条长链的逐次与逐阶段明细
